# macOS Event-Tap Lifecycle

Use this skill for native macOS `CGEvent` tap, `CFMachPort`, `CFRunLoop`, Accessibility, and callback/run-loop ownership work. It is for topology and lifecycle changes that must preserve an existing input policy, delivery contract, and downstream behavior.

## Non-negotiables

- Give the event tap, mach port, run-loop source, callback context, and final resource release one explicit owner thread. A lock around MainActor-owned framework resources is not an ownership transfer.
- Keep the framework callback synchronous and bounded: parse, read typed eligibility, admit or pass through, pair key events, record, signal, and return. Never await, hop to MainActor, call UI/permission/hardware APIs, or wait for downstream capacity from the callback.
- Use a bounded signal as a wake-up only. Keep FIFO order, pairing, and stale-session rules in the existing Domain gate; do not introduce a second delivery queue in Handler.
- Do not give the callback-to-main-thread handoff a capacity that suspends the app on overflow. The main thread drains the handoff within one run-loop turn and the Service keeps only the latest desired state, so coalescing already happens downstream; an overflow suspension punishes a fast key burst for a condition the design cannot reach, and if the main thread is blocked long enough to fill it, the block is the bug. Admission metrics (attempted, admitted, rejected, peak, wait) belong to a measurement campaign, not to the app.
- Treat lifecycle generations as capabilities. Capture the lifecycle and polling/revalidation generation before an `await`; re-check both and the current phase after it. A stale result is discarded, never converted into a new failure or suspension.
- Close admission before cleanup, release the old owner before reopening, and make repeated stop/release requests converge without duplicate release notifications.
- Keep shared locks narrow. Protect only handoff state, commands, waiters, and framework handles; release the lock before CoreGraphics/CoreFoundation, Accessibility, UI, Service, or run-loop calls. Snapshot diagnostic state under the lock, then emit logs outside it because logging can block a callback.
- Keep semantic reason conversions in one boundary mapping. Reuse it from lifecycle adapters instead of duplicating exhaustive switches that can drift when a new reason is added.
- Use checked continuations or an owner-run-loop command source for asynchronous start/stop handoff. Never join the callback or MainActor, and never use a semaphore to make teardown synchronous.
- Make process termination non-blocking and single-shot. Use AppKit's deferred termination reply, let cleanup win when it completes, and provide a bounded fallback that can reply without claiming native teardown completed.
- Permission suspensions (`missingPermission`, `permissionRevoked`) are the one state that watches for recovery: poll `AXIsProcessTrusted` once per second while waiting and call the contract's reopen path as soon as it answers true. An accessory app with no windows never receives the Finder reopen callback, so without this watch a granted permission is never noticed and only kill-and-relaunch recovers. System suspensions (tap disabled, creation failed) watch nothing; if macOS removed the tap the app does not fight for it. Keep the tap released in every suspended state so a late callback cannot revive a torn-down owner.
- Test at allowed Domain/Service seams. A Release offline pass proves modeled policy and Service behavior, not native callback scheduling, tap lifetime, Accessibility, OSD, or physical hardware behavior. Proof of native behavior is the installed app exercised by the user; a measurement apparatus is a separate decision the user makes explicitly, never a default (see `references/comparison-campaigns.md` only when they have).
- Treat Accessibility revocation while the tap is registered as the highest-risk path. Trust loss does not unregister the tap: the system stops delivering events without telling the process, freezes all input until it times the tap out, and only then signals the callback. The app cannot see the revocation earlier (see Failure patterns), so its job is to release the tap immediately on the disable signal and to have released it already in every suspended state; a tap that survives suspension is the bug, the freeze itself is not.

## Procedure

1. **Freeze the behavior surface.** Record the existing parser/filter, tap options and event mask, ordering, key-up pairing, lifecycle contract, consumer, instrumentation, and Service calls. During a topology experiment, change ownership and scheduling—not workload or policy.
2. **Trace the caller-to-effect path.** Identify the app lifecycle entry points, permission polling, sleep/wake/reopen paths, callback context, Domain gate, MainActor consumer, OSD, and Service. Search every caller before changing a signature or deleting a legacy router. After centralizing a suspension or diagnostic boundary, search every Handler, lifecycle adapter, owner, and callback context for direct calls to the Domain mutator and require them to route through that boundary; a conformance feed can exercise one duplicate while a second copy survives only on the native path.
3. **Sketch the ownership boundary.** Put all CoreGraphics/CoreFoundation resource fields on the owner thread. Expose only Sendable value results and asynchronous commands to the MainActor adapter. Keep the callback context independent of MainActor objects.
4. **Build the bridge.** Add a private owner-run-loop source that drains commands outside the lock. Use a bounded `AsyncStream` or equivalent only to coalesce wake notifications; the consumer must drain the Domain gate, not receive commands from the stream itself.
5. **Fence every await.** Distinguish `stale`, `enabled`, `disabled`, and `unavailable` outcomes where a status can race a lifecycle change. Keep lifecycle freshness in the Domain's stamped result, but keep poll/revalidation identity in a Handler-owned token when it is coordinator state; do not push Handler booleans or poller ownership into Domain merely to unit-test it. Check both identities before applying the observed result: a post-`await` guard in the coordinator is too late if the awaited interceptor already suspended or tore down state. Return a typed observation for the coordinator to fence and apply, or pass a currentness predicate into the async adapter and evaluate it immediately after the await, before any mutation. Unit-test Domain generation rules and prove the composite Handler fence through the candidate-bound conformance executable, not Handler unit tests. Re-check current phase before stopping polling, suspending, publishing, presenting, or submitting.
6. **Implement lifecycle ordering.** Sleep increments the generation, rejects new admission, discards queued work, and then requests owner teardown. Wake waits for teardown and requests fresh validation only for a lifecycle that slept active. An unavailable or suspended wake remains outside eligibility until an explicit reopen. Reopen cannot create a replacement while the previous owner is still active.
7. **Harden failure and termination paths.** Make owner teardown idempotent and perform the actual tap release on its owner thread. Model owner-thread readiness with typed `ready`, `failed`, and `stale` outcomes rather than a Boolean: a genuine run-loop/source startup failure must latch the owning creation-failure policy, while a concurrent stop or teardown race must remain stale and inert. Audit every path returning a public `.failed` result so the underlying failure is either handled at its owning boundary or carried explicitly to the caller; do not rely on one lower-level failure path to cover sibling exits. Ensure an unexpected run-loop exit tears down remaining resources. For termination, guard the AppKit reply with a thread-safe single-shot gate; emit completion diagnostics only when cleanup actually wins, not on fallback.
8. **Add seam proofs.** Cover FIFO order, stale pre-presentation delivery, sleep/suspension/wake, key-up pairing until owner release, lifecycle-plus-poller fencing, and any centralized mapping. Do not force Handler/CoreGraphics unit tests through mocks when the test scope excludes that boundary. One regression test per defect at the Domain gate or interceptor seam, with the expected value taken from the issue's expected line, not from the code.
9. **Reproduce before fixing.** Quit the installed app, relaunch it with the opt-in diagnostics flag (`open -n <bundle> --args --diagnose-input-lifecycle`), confirm the tap is actually active (one volume key shows the OSD) before the user performs the failing sequence, then read the unified log by process (`log show --last <n>m --predicate 'process == "<executable>"' --info --debug | grep <category>`); a subsystem predicate with `--style compact` can silently return a handful of lines. Order the recorded events and state exactly when the tap was released relative to trust loss before touching code; the fix targets the observed sequence, not the hypothesis. When adding a probe for a candidate signal, emit its diagnostic record before any guard so the log proves the signal arrived even when the guarded query still says the old value.
10. **Verify natively with the user.** `make build` the real app. A rebuilt ad-hoc-signed bundle silently loses its Accessibility grant even though the checkbox still appears on, so the app launches straight into missing-permission suspension with no tap and no OSD; until the bundle is signed with a stable Apple Development identity (see the SwiftPM build-tooling skill), before every manual test have the user toggle the grant off and on and confirm one OSD. Once the identity is stable, prove it: one grant, then a second `make build` must show the OSD with no toggle. Then have the user run the manual sequence: volume keys at normal pace and in bursts (OSD present, no duplicate system OSD), remove the Accessibility grant while running (expect the platform freeze of several seconds, then the app must be suspended with the tap released and volume keys passing through), quit and relaunch, grant in System Settings without reopening anything (the app must recreate the tap by itself within a second; confirm `permissionGranted` then `reopen` then `tapCreate returned` in the log), quit. Ten minutes on the installed artifact settles what days of modeled measurement cannot.
11. **When two topologies are compared**, install both as distinct bundle identities, run the same manual sequence on each, and decide from the observed difference. Identical failure on both means the varied dimension is not the cause; pick the simpler topology and move to the actual defect. Build a measurement campaign only when the user asks for one after seeing that result; the recipe, its pitfalls, and the retirement checklist live in `references/comparison-campaigns.md`.
12. **Explain lifecycle cases to the user in plain language before grilling them.** Present the tap as a barrier the app holds on the keyboard path (the whole system's input waits for the app's decision while it is held), then list every case as a table: situation, what the code does today, what the user observed. Frontier questions follow the table with all options visible and the recommended one first. The user decides policy from behavior, not from type or thread names.
13. **Explain the delivery design as a key's journey.** When the user asks whether the queue or handoff design is right, draw the numbered path of one key press (callback, handoff, main-thread consumer, Service) with the time budget of each stage, then name the stage that actually coalesces bursts. Judge every guard (capacity, overflow, metrics) against that path: a guard for a condition an upstream or downstream stage already prevents is removed, not tuned. The user's operating rule for a volume utility is "on any error do nothing, release the tap, and resume from the real hardware value on reopen"; propose designs that make that rule uniform rather than adding per-case options.

## Failure patterns

- **Tap outlives trust (platform limitation, not fixable in the app):** Accessibility is revoked while the tap is registered; the system stops delivering events to the process at once, freezes all input for several seconds, then disables the tap, and only that final `tapDisabledByTimeout` reaches the callback. No signal reaches the process at revocation time: `AXIsProcessTrusted` keeps answering `true` through the whole freeze window, the callback stays fast, and the distributed notification `com.apple.accessibility.api` does not fire for the revocation itself (it fires only for other edits to the Accessibility list, so an observer on it proves nothing on this path). Do not spend fix rounds hunting an earlier signal: the correct app behavior is to release the tap within a millisecond of `tapDisabledByTimeout`, record the limitation in an ADR, and tell the user to quit the app before revoking the grant.
- **Silent reopen:** an accessory app with no windows does not reach `applicationShouldHandleReopen` when the user opens it again from the Finder or Spotlight (no `reopen` record appears in the diagnostics log), so any recovery contract built on "the user reopens the app" is dead code; recover from a permission wait by polling the grant, and treat kill-and-relaunch as the only reopen the platform guarantees.
- **Dead process after live revocation:** once trust was revoked while the tap was active, the same process keeps reading `AXIsProcessTrusted` as true after regrant yet every later `CGEvent.tapCreate` returns nil. Do not retry creation in that process; record it as the platform limitation's second half and tell the user to quit and relaunch, then grant.
- **Rebuild resets the grant:** an ad-hoc signature changes on every rebuild, so TCC treats each build as a new app and the checkbox stays on while trust is false. Sign with a stable identity (see the SwiftPM build-tooling skill) so the grant survives rebuilds; until then, toggle the grant after every build before any manual test.
- **Untested fix round:** a rebuilt bundle is handed to the user for a revocation test while its grant is already void, so "no freeze" only means "no tap was ever created"; read the launch records (`missingAccessibility` at reopen) before interpreting a negative result.
- **Topology as scapegoat:** a system-input freeze is blamed on main-loop versus dedicated-thread scheduling before both are tried; identical behavior on both shows the cause is lifecycle policy, not scheduling.
- **Startup/stale conflation:** a Boolean owner-readiness result makes run-loop/source startup failure indistinguishable from a concurrent stop. Return typed `ready`/`failed`/`stale`; latch only the genuine startup failure and leave the stale race inert.
- **Stale-poller mutation:** an old permission/status poll suspends, tears down, or calls `stopPermissionPolling()` after a new poller started; compare the polling token as well as lifecycle generation before the awaited result reaches any mutating method. A coordinator guard after a mutating async call cannot undo stale damage.
- **Callback coupling:** a callback retains or invokes a MainActor adapter; pass a Sendable callback context instead.
- **Lock leakage:** a mutex remains held while calling framework, UI, permission, Service, run-loop, or logging APIs; snapshot state, unlock, then emit.
- **Duplicated semantic mapping:** the same suspension-to-diagnostic switch appears in multiple adapters; centralize the conversion so new cases cannot drift.
- **Ambiguous release:** both the consumer and owner finish the wake stream or clear tap ownership; choose one owner and make the operation idempotent.
- **Proxy proof:** an offline harness or successful compile is reported as native tap, callback, Accessibility, OSD, or hardware proof.
- **Overflow as policy:** a fast burst of volume keys suspends the app until reopen because the handoff capacity was treated as a product limit; capacity, if kept at all, is invisible (excess key passes through, app stays active) because the Service's single desired state already coalesces.
- **Unverified refactor count:** a delegated test refactor reports a lower test count; verify the arithmetic yourself (tests before minus tests whose subject was deleted equals tests after) and grep the suites for every original `@Test` name before committing, because a subagent that drops a test to make the build pass reports success.
- **Cross-process clock conflation:** parent resource samples and child phase timestamps are compared as absolute nanoseconds without a proven shared epoch; observe child boundary records on the parent's clock (or calibrate explicitly) and require nonempty phase attribution, because reconstructing with the same invalid comparison is tautological.
- **Unproven escape hatch:** `@unchecked Sendable` is added without an explicit confinement invariant and complete lock coverage; the annotation must describe a proven owner, not silence strict concurrency.
- **Nested-watchdog orphan:** the outer runner kills only its direct apparatus child while the candidate or compiler descendants live in another group; make the outer command own the complete inherited process group and prove descendant cleanup.
- **State-only evidence validation:** analysis trusts report paths after checking only campaign-level tool digests; bind each report by digest and re-run its correctness, reconstruction, and artifact checks before computing metrics.
